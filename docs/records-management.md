# Records management and document corrections

For an existing database run `php scripts/setup-records-management.php` before deploying the updated web app. This repeatable setup creates only `record_changes`; it does not change existing documents, accounts, or catalog names. Fresh installations include the table in `database/schema.sql`.

Personnel profiles also require `php scripts/setup-personnel-details.php` on existing databases. This adds nullable `email`, `position`, and `campus` columns. To enrich existing mapped personnel from the original PAD faculty table, explicitly pass its configuration path: `php scripts/setup-personnel-details.php C:\VertrigoServ\www\sam.pad\db.php`. The source is read only; enrichment fills NULL values by `legacy_profile_id` and preserves saved details. Fresh installations already include these columns. The document-type/personnel import also carries these fields on future imports.

## Permissions and editable fields

Only an assigned **active OVP Central Records role**, with an active non-OP routing office, can use the Management sidebar: Document Particulars, Faculty / Personnel, and Document Sources. Having an administrator or PAD role does not grant these permissions. A multi-role user must explicitly select Central Records.

Central Records can correct **particulars / document name** on visible records at any workflow status, including completed and imported records. This updates `description` and regenerates the searchable `subject` from the first 255 Unicode characters. A nonempty change reason is required. No other document field is accepted by this operation. Existing custody, numbering, PAD decision, receipt/routing actions, and attachment operations retain their existing rules.

The originating office can edit document type, source catalog selection, linked personnel, and applicable Travel Order fields while preparing an unsent office document or after receiving a return for correction. The active role must be SKSU Officials or OVP PAD. Central Records cannot use this owner operation, including for its own registrations. The holder of another office's document receives no ownership edit permission. Owners cannot change particulars, file codes, recorded registration dates, custody, workflow status, or PAD decisions through this operation.

Ownership uses the recorded `source_office_id` of an office-origin document. The source-name catalog has no authenticated-office mapping, so it cannot grant ownership. Outside intake does not acquire owner editing simply because Central Records encoded it. PAD's explicit delivery of a returned-for-correction decision restores owner editing after receipt, as does an ordinary issue Return followed by owner receipt.

## Catalogs and history

Central Records can add names, rename entries, and activate/deactivate them. There is no catalog deletion endpoint. Deactivated entries disappear from new registration selections. Existing selected inactive entries remain usable during owner editing. Historical personnel names and source names remain snapshots: unrelated edits do not replace them with the current catalog spelling. New selections use the current catalog names.

Adding personnel requires a full name, valid email address (up to 191 characters), position/designation (up to 255), and actual campus (up to 80). Duplicate email addresses are rejected, including inactive entries. The personnel form includes these required fields on add and edit; the list displays and searches them. Older imported details may be incomplete or contain placeholder emails generated by the old system. Recorded values are preserved for review; the form never generates email addresses. Partial API updates preserve omitted existing fields, so older incomplete entries can still be deactivated without inventing details.

The legacy `acc_type` field is an account permission classification, not a personnel designation. It is deliberately excluded from this form and from import into the personnel catalog. Adding an email here does not create or approve a login. Contact details appear only in the Central Records management API; registration dropdowns continue to receive only personnel IDs and names.

The legacy source/personnel import scripts preserve entries already changed through Records Management, so rerunning setup cannot overwrite locally corrected names.

Document edits and catalog changes save the previous values, new values, reason, editor name/role/office and UTC time in `record_changes`, in the same transaction as the change. Document details show a separate Correction history with Manila display times. Correction events do not alter custody durations or rewrite routing remarks. The audit table is protected from Database management clearing and intentionally retains evidence if operational records or accounts are deleted.

Forms send a version fingerprint. The service locks and rereads the record before applying an edit; a stale version or changed workflow permission is rejected. Requests containing unauthorized fields are rejected instead of silently ignoring them.

## API

- `PATCH /api/doc_router/documents/{reference}/particulars`: `description`, `version`, `reason`.
- `PATCH /api/doc_router/documents/{reference}/details`: permitted owner fields, `version`, `reason`. Updates may be partial; changing from Travel Order to another type requires clearing the travel fields.
- `GET /api/doc_router/routing/management/{personnel|sources}`: catalog rows with active status and version.
- `POST /api/doc_router/routing/management/{personnel|sources}`: `name`, optional boolean `is_active`, `reason`. Personnel also requires `email`, `position`, `campus`.
- `PATCH /api/doc_router/routing/management/{personnel|sources}/{id}`: `name`, optional boolean `is_active`, `version`, `reason`. Personnel accepts `email`, `position`, `campus` and preserves omitted values.

The existing shared `/api/documents` and `/api/routing` aliases apply the same permissions. There are no management write endpoints for other roles.

Validate with `php tests/office-routing-smoke.php`, which includes `tests/records-management-cases.php` against a disposable database. The web application uses `npm test` and `npm run build`.
